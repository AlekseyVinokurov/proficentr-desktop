# U01 + S01: обновления, выпуск и восстановление

## Граница доверия

Версия приложения 0.2.0; протокол обновления 1, Windows x86-64, PyInstaller onedir. Источник фиксирован в `updates.py`: `AlekseyVinokurov/proficentr-desktop`. API `/releases/latest` запрашивается при запуске не чаще раза за 24 часа (время попытки хранится отдельно от настроек хранилища); ручная проверка доступна всегда. Стабильная версия — строго `vX.Y.Z`, сравнение числовое. Нет токенов пользователя, регистрации или обязательного обновления. Ошибка сети не препятствует работе. Проверки и загрузки выполняются в QThread. При выходе программа дожидается завершения сетевой операции; отдельные сетевые ожидания ограничены таймаутом.

Релиз содержит `Proficentr-X.Y.Z-Windows.zip`, `manifest.json`, `manifest.sig` (64 байта). Ed25519 подписывает точные байты JSON, включая формат, версию, имя, размер, SHA-256, платформу, минимальную версию updater и версию схемы. Подпись проверяется до загрузки ZIP; подписанный размер ограничивает загрузку. Архив проверяется до распаковки. Недопустимы выход за корень, ссылки, Windows ADS/зарезервированные имена, повторные имена и превышение предельного размера. Публичный ключ встроен; ключ из релиза, настройки или переменной окружения не принимается. Переходы HTTPS разрешены только в официальную инфраструктуру GitHub. Изменение доверенного ключа требует проверенного выпуска; автоматическая ротация не реализована.

Приватный ключ создан для этого репозитория и передан напрямую в GitHub Environment Secret `release/RELEASE_ED25519_PRIVATE_KEY`, без сохранения в файлах или логах. Окружение `release` требует подтверждения владельцем, принимает только теги `v*.*.*`. Получить секрет обратно через GitHub нельзя. При потере/компрометации ключа нужен отдельный план ротации и ручная установка доверенной сборки; не заменяйте ключ незаметно. GitHub administrators могут менять настройки защиты; это необходимо учитывать при разграничении прав.

## Установка

В «Настройки → О программе» отображаются версия, официальный источник, статус и описание изменений обычным текстом. После подтверждения пакет загружается и распаковывается в новый соседний каталог `.proficentr-update-<id>/staged/Proficentr`. Установка доступна только из Windows EXE. Данные должны быть вне каталога программы. Нужны права записи в родительскую папку и место одновременно для старой версии, helper, ZIP и новой версии. При недостаточных правах следует вручную распаковать официальный ZIP в пользовательский каталог, например `%LOCALAPPDATA%\Programs`, и запустить EXE; настройки хранилища сохраняются. UAC не обходится.

Helper — отдельный небольшой `ProficentrUpdater.exe`, собранный без Qt и скопированный в рабочий каталог обновления. Он работает кратковременно, не требует службы и не удерживает файлы установленной версии. Он ждёт завершения PID, блокирует обычные запуски, запускает новую версию с `--update-probe` на проверенной копии рабочей базы, затем переименовывает текущий каталог в `<имя>.previous`, а подготовленный — в текущий. Новый EXE запускается с подтверждением готовности после открытия базы и построения окна. Не используются shell, служба или административные права. Блокировки запуска относятся к одной пользовательской конфигурации; совместная работа нескольких пользователей с одной SQLite не поддерживается.

При отказе пробного запуска рабочие программные файлы не меняются. При отказе нового запуска они возвращаются на прежнее место; helper сообщает о сбое, не запускает старый EXE автоматически и не восстанавливает базу. Каталоги `.previous`, рабочие файлы и результат `result.txt` сохраняются для восстановления. Следующее обновление заблокировано, пока `.previous` не проверен и не перенесён пользователем. После успешной работы можно вручную удалить прежние программные файлы и рабочий каталог обновления, закрыв приложение. Не удаляйте хранилище и настройки.

## SQLite и восстановление

Ранее выполненные миграции не изменены. Перед новыми миграциями существующей базы под блокировкой записи создаётся Backup API-копия с учётом WAL в `database/migration-backups/<id>.sqlite3`; проверяется `integrity_check`. Миграции применяются сначала к дополнительной копии, затем в транзакции к рабочей базе. При ошибке рабочая транзакция откатывается, резервная копия сохраняется. Более новая или нарушенная последовательность схемы отклоняется. Новая пустая база при недоступном настроенном хранилище не создаётся. Первичная инициализация пустой базы не требует резервной копии.

Автоматический откат EXE не означает откат SQLite. Если новая версия успела применить миграции, старая программа может отказаться открывать базу. Это безопаснее скрытой потери новых записей. Остановите все экземпляры, сохраните целиком текущее хранилище вместе с WAL/SHM и резервными копиями; используйте совместимую исправленную версию. Возвращать резервную базу можно только отдельной осознанной операцией после оценки записей, внесённых после её создания. Автоматического объединения или восстановления базы нет.

После отключения питания между переименованиями версию можно восстановить вручную: при закрытых процессах сохраните каталоги, верните `.previous` на прежнее имя, если рабочая папка отсутствует, затем проверьте совместимость схемы. Helper не является универсальным транзакционным установщиком и не восстанавливается автоматически после отключения питания. Подписанные пользовательские документы не затрагиваются.

## Защищённый выпуск

Обычные push/PR запускают `windows.yml`: фиксированные зависимости из `requirements-release.txt`, pip check, pytest, Bandit, политика безопасности, Gitleaks по истории, pip-audit, onedir, smoke и проверка переключения реальных EXE в Windows. Артефакты Actions не используются приложением для обновлений.

Отдельный `release.yml` запускается вручную **с ref самого тега** (например, `gh workflow run release.yml --ref vX.Y.Z -f tag=vX.Y.Z`), а не с main: окружение разрешает только релизные теги. Существующий тег `vX.Y.Z` должен указывать на текущий `main`; workflow требует успешной Windows-проверки и подтверждения окружения `release`. Версия тега должна совпасть с приложением и pyproject; до публичного выпуска необходимо утвердить LICENSE. Только шаг подписи получает секрет. Workflow создаёт Ed25519-манифест, [GitHub Artifact Attestations](https://docs.github.com/en/actions/how-tos/secure-your-work/use-artifact-attestations/use-artifact-attestations) и GitHub Release с описанием CHANGELOG. Attestation подтверждает происхождение сборки, а встроенный updater проверяет Ed25519. Authenticode пока отсутствует. Первый стабильный релиз этой задачей не публикуется.

Владелец должен включить правила для `main`: PR, успешный Windows job, проверку CODEOWNERS, запрет force push/удаления, ограничение обхода администраторами по принятой организационной модели. Для `v*` — ограничить создание/изменение/удаление тегов ответственными за выпуск. Ограничить права Actions и публикации, защитить аккаунты 2FA/passkeys, включить Private Vulnerability Reporting и secret scanning, если доступны. CODEOWNERS сам по себе не обеспечивает обязательного review. В проекте с одним владельцем второе независимое подтверждение требует второго доверенного сопровождающего. Настройки main/тегов автоматически не изменялись.

## Пределы проверки

Windows CI проверяет транспорт/подпись на локальных синтетических fixtures, распаковку реального ZIP, запуск внешнего frozen helper, переключение двух onedir-копий, подтверждение нового EXE и сохранность вымышленных сведений, вложения и настроек. Ключ тестов создаётся в памяти; встроенный ключ EXE не заменяется. Ошибки подписи, хэша, ZIP, пробного запуска, запуска и миграций проверяются отдельно целевыми тестами. Проверка настоящего скачивания и перехода между двумя опубликованными стабильными версиями возможна после их отдельного выпуска. Это ограничение нельзя считать проверкой уже работающего публичного канала.
