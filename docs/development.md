# Техническое руководство

Здесь собраны инструкции разработчика, устройство локального хранилища и ограничения реализованных модулей. Пользовательское описание и установка — в [README](../README.md). Этапы и результаты проверок — в [состоянии проекта](project-status.md); протокол обновлений, выпуск и восстановление — в [updates.md](updates.md); правила безопасности — в [SECURITY.md](../SECURITY.md).

Приложение предназначено для Windows; основная среда разработки — Python 3.12, VS Code, WSL Ubuntu и Git. Первый пользователь — ЧУ ДПО «Профицентр-2», но архитектура не привязана к одной организации.

## Запуск из исходного кода

Нужен Python 3.12. В Windows PowerShell:

```powershell
python -m venv .venv
.venv\Scripts\python -m pip install -e ".[test]"
.venv\Scripts\python -m proficentr
```

В Linux / WSL:

```bash
python3.12 -m venv .venv
.venv/bin/python -m pip install -e '.[test]'
.venv/bin/python -m proficentr
```

Для обычного окна Linux нужен графический дисплей (в WSL — WSLg). Проверка без дисплея:

```bash
QT_QPA_PLATFORM=offscreen XDG_CONFIG_HOME=/tmp/proficentr-smoke-config PROFICENTR_DATA_DIR=/tmp/proficentr-smoke .venv/bin/python -m proficentr --smoke-test
.venv/bin/python -m pytest -q
```

`--smoke-test` открывает окно, проверяет все переходы и автоматически завершает приложение. Тесты используют временные базы и синтетические данные.

Для воспроизведения фиксированного окружения CI вместо установки `.[test]` установите `requirements-release.txt`, затем проект без повторного разрешения зависимостей:

```text
python -m pip install -r requirements-release.txt
python -m pip install --no-deps -e .
python -m pip check
```

Лёгкие проверки безопасности в этом окружении:

```text
python scripts/security_check.py
python -m bandit -r src -q
python -m pip_audit -r requirements-release.txt --disable-pip --no-deps
```

CI дополнительно проверяет историю Git через Gitleaks; исключён только конкретный отпечаток публичного ключа. Обновляйте фиксированные зависимости осознанно, с проверкой известных уязвимостей. Эти инструменты не доказывают отсутствие всех уязвимостей.


## Данные

При первом запуске выберите пустую локальную папку, например `D:\ProficentrData` (кириллица и пробелы допустимы). Отмена выбора завершает запуск без создания базы. Каталог не связан с расположением EXE. В нём автоматически создаются:

```text
database/proficentr.sqlite3
documents/
attachments/
templates/
organization/
exports/
```

Путь сохраняется атомарно в отдельном пользовательском файле настроек: Windows — `%LOCALAPPDATA%\Proficentr\settings.json`; Linux — `$XDG_CONFIG_HOME/proficentr/settings.json`, по умолчанию `~/.config/proficentr/settings.json`. Обновление или переустановка приложения не меняет выбранный путь. Не удаляйте этот файл при обновлении. Если настроенный диск или база недоступны, приложение сообщает об ошибке и не создаёт пустую замену.

Старая база P01 (`%LOCALAPPDATA%\Proficentr\proficentr.sqlite3` либо `$XDG_DATA_HOME/proficentr/proficentr.sqlite3`, по умолчанию `~/.local/share/proficentr/proficentr.sqlite3`) обнаруживается автоматически: SQLite Backup API создаёт проверенную копию в `database/`, а исходный файл сохраняется. При конфликте двух баз автоматический выбор отменяется.

На странице **Настройки** показаны каталог, путь к SQLite и состояние доступности. Кнопка выбора папки предлагает перенести базу и содержимое пяти каталогов архива. Назначение должно быть пустым и находиться вне исходного хранилища. Перед переносом закройте другие экземпляры приложения. Проверяются запись, свободное место (с запасом 16 МиБ) и конфликты; база копируется через SQLite Backup API с учётом WAL и проверяется `integrity_check`. Новый путь сохраняется только после успешного копирования. При ошибке прежняя конфигурация и исходные данные сохраняются. После успеха приложение закрывается: запустите его снова. Старую копию автоматически не удаляем; перед её ручным удалением убедитесь, что новый архив работает.

Для явного задания пути, в том числе в CI, сохранена `PROFICENTR_DATA_DIR` — абсолютный локальный каталог (PowerShell: `$env:PROFICENTR_DATA_DIR = 'D:\ProficentrData'`). Переменная имеет приоритет; при первом использовании хранилище инициализируется, путь сохраняется в настройках. При активной переменной перенос через интерфейс отключён: уберите её и перезапустите приложение. Для тестового запуска задавайте отдельный каталог данных и конфигурации.

Храните данные вне исходников и папки EXE. Приложение отклоняет UNC, подключённые сетевые диски Windows, известные сетевые файловые системы Linux и явно распознанные папки OneDrive, Dropbox и Google Drive (по имени либо известной переменной окружения). Все клиенты синхронизации автоматически определить невозможно: пользователь должен выбирать обычную локальную папку. Совместная работа через сетевой SQLite не поддерживается. Для резервного копирования закройте приложение и скопируйте каталог данных. Символические ссылки в каталогах архива при переносе отклоняются.

Схема содержит `schema_migrations`, добавленную миграцией № 2 таблицу `training_center`, добавленную миграцией № 3 таблицу `students`, добавленную миграцией № 4 таблицу `counterparties`, добавленную миграцией № 5 таблицу `programs` добавленные миграцией № 6 таблицы `training_groups` и `trainings` и реестр `document_templates` миграции № 7 и таблицы `contracts`, `contract_trainings`, `contract_sequences` миграции № 8; таблицы `enrollment_orders`, `enrollment_order_trainings`, `enrollment_order_sequences`, `training_enrollments` миграции № 9. Миграции в `database.py` применяются последовательно в транзакции; новые добавляются в конец списка. Более новая схема отклоняется, соединение закрывается при выходе и при ошибке запуска. Порядок резервирования, пробных миграций и восстановления описан в [updates.md](updates.md#sqlite-и-восстановление).

## Реестр слушателей

В разделе **Слушатели** можно добавить человека, найти, открыть и исправить его карточку. Таблица содержит ФИО, дату рождения, телефон и email. Поиск учитывает частичные совпадения, работает с русскими буквами без учёта регистра, а для телефона и СНИЛС допускает ввод с пробелами и разделителями. После сохранения список обновляется, прежний фильтр сбрасывается и сохранённая строка выделяется.

Для создания обязательны фамилия, имя и дата рождения; возраст на текущую дату компьютера должен составлять 18 лет или больше. Пограничный возраст проверяется по месяцу и дню рождения (для 29 февраля в невисокосном году — с 1 марта). При будущем зачислении потребуется самостоятельная проверка возраста на дату начала обучения. Даты вводятся и хранятся как `ГГГГ-ММ-ДД`. Избыточные пробелы убираются, регистр имён сохраняется. Отчество, гражданство, контакты, паспорт, образование, работа и примечание могут быть заполнены позже. Паспортная серия проверяется как 4 цифры, номер — 6, код подразделения — `000-000`; дата выдачи не может предшествовать рождению или находиться в будущем.

СНИЛС необязателен; если введён, проверяются формат и контрольная сумма. В базе сохраняются 11 цифр без разделителей. Для старых номеров до `001-001-998` включительно применяется проверка формата без контрольной суммы; нулевой номер отклоняется. Алгоритм описан в [правилах расчёта контрольной суммы ТФОМС](https://rostov-tfoms.ru/services/zasedaniya-rabochih-grupp/erp/pravila-rascheta-kontrolnoj-summy-snils). Проверка не подтверждает принадлежность номера человеку и не обращается к внешним сервисам.

Перед сохранением проверяются точное совпадение заполненного СНИЛС и возможное совпадение ФИО с датой рождения. Предупреждение различает эти причины, позволяет открыть выбранную существующую карточку либо явно сохранить отдельную запись. Открытие найденной карточки отменяет текущие несохранённые изменения. Однофамильцы допустимы; автоматического объединения и уникальности ФИО нет. Сохранение карточки выполняется транзакционно. При отмене и закрытии изменённой формы можно сохранить изменения, отказаться от них или продолжить редактирование.

Постоянный идентификатор — внутренний `students.id`, который не меняется при исправлении ФИО, паспорта или СНИЛС. Повторные обучения ссылаются на существующего слушателя через `trainings.student_id`; программа и необязательная группа имеют собственные внешние ключи. Договоры связываются с выбранными обучениями через `contract_trainings`. Физическое удаление через интерфейс отсутствует. Изменение карточки не должно менять исторические документы: в следующих этапах они будут хранить снимок данных, а исправления зарегистрированных сведений — пользователя, дату, старое и новое значение в журнале аудита. Сейчас снимки реквизитов слушателя, аудит, роли и архивный статус карточки слушателя не реализованы.

Требования к защите и сообщениям об уязвимостях — в [SECURITY.md](../SECURITY.md). Модуль слушателей не пишет данные в логи; диагностические сообщения SQLite заменяются нейтральными сообщениями. Все данные автоматических тестов вымышлены.

## Организации-заказчики

Реестр `counterparties` и `CounterpartyRepository` отделены от `training_center` и `TrainingCenterRepository`. Типы — `legal_entity` (юридическое лицо) и `sole_proprietor` (ИП); физические лица как заказчики здесь не учитываются. Постоянный внутренний ID сохраняется при исправлении реквизитов. Для создания достаточно типа и полного наименования; сокращённое наименование, контакты, адреса, банковские реквизиты, представитель, основание полномочий, реквизиты доверенности и примечание необязательны. Форма прокручивается; сохранение выполняется транзакционно, закрытие изменённой карточки предлагает сохранить, отказаться от правок или продолжить редактирование. Физического удаления через интерфейс нет.

Для заполненных реквизитов проверяется формат: ИНН — 10 цифр у юридического лица и 12 у ИП; ОГРН — 13, ОГРНИП — 15; КПП — 9 знаков с допустимыми латинскими буквами в позициях 5–6; БИК — 9 цифр; банковские счета — 20 цифр; email — локальная проверка формата. Контрольные суммы налоговых и банковских реквизитов не проверяются, обращения к внешним реестрам отсутствуют. Для ИП КПП не применяется; при смене типа заполненный КПП очищается только с подтверждением и только в форме до сохранения.

Поиск учитывает полное и сокращённое наименования без учёта регистра русских букв, ИНН и телефон; для числового запроса допускаются пробелы и разделители. Возможные дубли определяются по точному заполненному ИНН либо полному/сокращённому наименованию без учёта регистра и избыточных пробелов. Текущая карточка исключается. Предупреждение позволяет открыть найденную карточку, отменить сохранение или явно сохранить отдельную запись; автоматического объединения и уникальности ИНН нет. Открытие найденной карточки отменяет текущие несохранённые правки. После сохранения фильтр очищается и запись выделяется. Ошибки репозитория не раскрывают содержимое карточек и исходные сообщения SQLite; данные не записываются в логи.

Одна организация в дальнейшем сможет быть заказчиком нескольких договоров и обучения нескольких слушателей независимо от их места работы. Договоры ссылаются на существующего заказчика через `contracts.counterparty_id`; связь с обучениями хранится отдельно. Учёт оплат не реализован. При регистрации договоров потребуются снимки реквизитов: изменения карточки не должны менять исторические документы. Эта задача и договоры с физическими лицами относятся к P03.

## Образовательные программы

Таблица `programs`, модель `Program` и `ProgramRepository` образуют отдельный справочник. Направление (`dpo` / `po`) и вид хранятся структурированно. В ДПО предусмотрены повышение квалификации и профессиональная переподготовка; в ПО — профессиональная подготовка по профессиям рабочих и должностям служащих, переподготовка и повышение квалификации рабочих и служащих. Совместимость направления и вида проверяется в модели и ограничением SQLite; смена направления в форме сбрасывает прежний вид и требует выбрать подходящий.

Обязательны полное наименование, направление, вид и положительное целое число академических часов. Произвольный предельный срок обучения не задан; хранение целого ограничено числовым форматом SQLite. Необязательны сокращённое наименование, внутренний код, квалификация/профессия/должность, разряд/категория, дата/номер/другие сведения об утверждении, редакция и примечание. Квалификация и разряд заполняются только при применимости, одинаковых требований ко всем видам нет. Дата проверяется как существующая дата `ГГГГ-ММ-ДД`; нормативные ограничения объёма, зачисления и аттестации не реализованы. Стоимость и даты конкретного обучения к справочнику не привязаны.

По умолчанию видны активные программы; фильтры позволяют выбрать направление и активные/архивные/все записи. Поиск работает по полному и сокращённому наименованию и внутреннему коду без учёта регистра русских букв и избыточных пробелов. Совпадение полного наименования или заполненного кода вызывает предупреждение, включая архивные программы; текущая карточка исключается. В предупреждении видны вид, часы, редакция и статус. Можно открыть найденную карточку, отменить сохранение или явно сохранить отдельную программу, в том числе с одинаковым названием и другой редакцией. Автоматического объединения и уникальности названия/кода нет.

«В архив» и «Вернуть в активные» изменяют только статус с подтверждением, сохраняя ID и все остальные сведения. Физического удаления через интерфейс нет. Карточки можно редактировать и в архиве; при закрытии изменённой формы предлагается сохранить, отказаться от правок или продолжить работу. После сохранения карточки фильтры переключаются так, чтобы показать и выделить её; после архивирования кнопкой сохраняется выбранный фильтр активности.

Постоянный ID, обозначение редакции и архивный статус позволяют хранить отдельные старые редакции. Обучения ссылаются на программу и сохраняют её снимок при создании: исправления справочника не меняют эти сведения автоматически. Связи с документами пока нет. Полноценное версионирование, правила зачисления, документы и ФИС ФРДО здесь не реализованы; будущие выгрузки должны использовать официальные шаблоны отдельно для ДПО и ПО.

## Учебные группы и обучения (P03.1)

Раздел «Группы» содержит вкладки «Учебные группы» и «Индивидуальное обучение». Группа ссылается на одну существующую активную программу, без обязательного заказчика или договора. Обучение — отдельная запись с постоянным ID, ссылками на слушателя, программу и необязательную группу. Один слушатель может иметь несколько обучений. Состояние `preparation` («Подготовка») не означает юридического зачисления; само создание подготовительной записи не присваивает номер приказа и не подтверждает зачисление.

Плановые даты хранятся как ISO-даты; окончание не раньше начала. Исторические даты допустимы. Отдельное `created_at` устанавливается SQLite в UTC при создании и сохраняется при правках. Возраст проверяется на плановую дату начала существующей функцией `is_adult`, включая достижение 18 лет родившимися 29 февраля с 1 марта невисокосного года. Требования к образованию и юридические основания зачисления здесь не проверяются.

При добавлении в группу её программа и даты подставляются по умолчанию. Даты отдельного обучения можно исправить; изменение дат группы не переписывает уже созданные обучения, о чём сообщает форма. Несовпадение программ запрещено репозиторием и составным отложенным внешним ключом SQLite. Повторный активный состав `(group_id, student_id)` запрещён частичным уникальным индексом. Несколько выбранных слушателей добавляются одной транзакцией; при дубле или ошибке весь набор откатывается. Пересечение периодов одного слушателя по одной программе требует подтверждения, но разрешено.

`program_snapshot` содержит JSON со значениями названия, направления, вида, часов, кода, редакции, квалификации/профессии и разряда. Правки справочника не меняют снимки; обычное сохранение примечания также их не обновляет. На этапе подготовки снимок можно явно обновить в форме. Изменение программы индивидуального обучения требует подтверждения. Изменение программы группы с существующими связями требует отдельного подтверждения и атомарно меняет программу и снимки всех её подготовительных записей, включая исключённые; даты и ID сохраняются. Проверяется отсутствие оформленных записей, возможные пересечения требуют дополнительного подтверждения. После подтверждения подписания приказа P03.4 такие изменения запрещены репозиторием и триггерами SQLite.

Архивирование и восстановление группы меняют только её активность. Для добавления, правки обучений и исключения сначала нужно восстановить группу. Исключение ошибочно добавленной записи допустимо только при подготовке: состояние `excluded` сохраняет её ID, связи и снимок, скрывая из текущего состава. Включите «Показать исключённые подготовительные записи» для просмотра истории состава. Повторное добавление создаёт новую запись. Основная карточка и другие обучения сохраняются. Физического удаления через интерфейс нет.

Поиск слушателей возвращает только ID, ФИО и дату рождения, максимум 100 совпадений; пустой поиск не загружает весь реестр. Состав и индивидуальный список читают только отображаемые поля, без паспортов и СНИЛС. Формы сохраняют изменения только по явному действию; отмена и отказ от правок не записывают данные. Новых зависимостей и сетевых функций нет. Windows update smoke проверяет сохранность активной/архивной групп, групповых/индивидуального обучений и снимков существующим U01.

## Универсальные DOCX-шаблоны (P03.2)

В **Настройки → Шаблоны документов** работает реестр `document_templates` (миграция № 7). Одна запись — неизменяемая версия: ID, тип, вариант, название, целочисленная версия, относительный путь `templates/<UUID>.docx`, SHA-256, время добавления UTC и активность. Версия назначается в транзакции `BEGIN IMMEDIATE` для точной пары типа и варианта; уникальны номер версии и путь. Частичный уникальный индекс допускает не более одной активной версии пары. Новую версию можно зарегистрировать неактивной; активация старой позволяет вернуться к прежней форме. Деактивация не удаляет файлы.

`TemplateRepository` хранит только проверенный DOCX. Проверка и пробная генерация выполняются до изменения реестра. Файл публикуется перед INSERT и commit; при ошибке SQL новая копия удаляется, прежняя активная версия откатывается. Аварийное завершение между записью файла и commit может оставить непривязанный файл, но не меняет старые версии. Все рабочие файлы получают случайные имена; исходные имена и пользовательские варианты не используются как пути. Символические ссылки и выход за пределы хранилища запрещены. Старые версии не удаляются и не перезаписываются через интерфейс; прямые изменения файла обнаруживаются по SHA-256 при использовании, активации и выгрузке. Это контроль целостности, а не защита SQLite от намеренного изменения владельцем диска.

`docx_context.py` задаёт закрытую схему и вымышленные данные. `docx_engine.py` не зависит от Qt/SQLite: `generate_document(TemplateSource(path, sha256), data, destination)` проверяет хеш и создаёт новый DOCX. Контекст содержит только точные встроенные `dict`, `list`, `str`, `int`, конечный `float`, `bool` и `None`, без подклассов, моделей, функций и путей. Неизвестные ключи, управляющие символы, чрезмерные строки и объём данных отклоняются. `program.name` должен поступать из снимка `program_snapshot.full_name`, `program.hours` — из того же снимка. Подготовка контекста реальных юридических документов будет отдельным сценарием; текущий UI берёт только вымышленные данные и не читает карточки в контекст генератора.

Оформление и структуру Word сохраняет `docxtpl`, работающий через `python-docx` и `lxml`. Язык ограничен поверх `ImmutableSandboxedEnvironment` Jinja: очищены globals/filters/tests, отключены Python-атрибуты и вызовы, отсутствует загрузчик файлов, используется `StrictUndefined` и XML autoescape. До компиляции проверяется AST: разрешены только известные поля, простые условия и один уровень цикла по `students`. Запрещены арифметика, вызовы, фильтры, import/include, макросы, set и доступ к произвольным объектам. Проверяются все ветви, включая неисполняемые, основной текст, колонтитулы, сноски и поддерживаемые основные свойства; теги в неподдерживаемых частях отклоняются. Перед выполнением ограничиваются сложность AST, глубина условий и консервативная оценка объёма результата. Эти ограничения дополняют sandbox, поскольку сам sandbox не ограничивает расход памяти и процессорного времени. Основание: [docxtpl](https://docxtpl.readthedocs.io/en/stable/) и [Jinja sandbox](https://jinja.palletsprojects.com/en/stable/sandbox/).

Пакет DOCX проверяется в памяти без распаковки и разрешения внешних ссылок: ограничения размера/сжатия/числа частей, CRC, обязательные части, закрытый набор имён и типов, корректный XML через `defusedxml` без DTD и сущностей. Все отношения должны быть внутренними и указывать на допустимую часть пакета. Макросы, вложения, OLE/ActiveX, внешние отношения, прямые XML-ссылки на ресурсы, привязки данных, DDE и прочие активные инструкции Word отклоняются; разрешены только поля нумерации страниц. Поддерживаются обычные растровые изображения и инертные customXml-части; неподдерживаемые части отклоняются, а не молча удаляются. Библиотеки не получают разрешения читать внешние файлы или ресурсы шаблона.

Результат полностью формируется и проверяется в памяти, затем записывается во временный файл рядом с назначением, синхронизируется и публикуется без перезаписи. В Windows используется `rename` с отказом при существующем пути, в POSIX — атомарный hard link; при отсутствии поддержки файловой системой операция возвращает ошибку. Неудачная генерация не оставляет частично записанный документ по целевому пути. При аварийном завершении возможен временный `.docx-*.tmp`. Существующие документы не заменяются. Лимиты и синтаксис приведены в [инструкции по шаблонам](templates.md).

Копии для редактирования создаются в `exports/template-edits/`, тестовые документы — в `exports/template-tests/TEST-unregistered-<UUID>.docx`. Внешний редактор запускается только по действию пользователя и только для проверенной локальной копии DOCX, без shell. Для работы требуется установленный обработчик DOCX (Microsoft Word или другой редактор). Тестовая генерация не регистрирует юридические документы и не присваивает юридические номера. Шаблоны и экспортированные файлы находятся вне EXE и переносятся вместе с хранилищем. Механизм U01/S01 и прежние миграции не изменены. Windows smoke дополнен проверкой генерации внутри frozen EXE и сохранности реестра, файлов версий и старого результата при обновлении.

Для следующих этапов сохранены решения: генератор независим от UI, при регистрации юридического документа сохраняются снимки реквизитов слушателя, заказчика, учебного центра и программы. Файлы документов получают путь через `Storage.document_directory` (`documents/YYYY/MM/category/`), номер управляется реестром SQLite отдельно от имени файла. Исторические документы сохраняют исходные даты и номера отдельно от даты внесения; зарегистрированные и подписанные оригиналы не перезаписываются при изменении справочника или шаблона. ДПО и ПО сохраняют отдельные правила. P03.3 реализует договоры; заявления, согласия, приказы и протоколы пока представлены только типами шаблонов. Собственные юридические тексты не создаются. Выпускные документы, ФРДО, подписи, PDF, роли и аудит не реализованы.

## Договоры на обучение (P03.3)

`Contract`, `ContractRepository` и отдельная страница **Документы → Договоры** используют существующие справочники и DOCX-движок. Миграция № 8 добавляет реестр договоров, упорядоченные связи с обучениями и счётчики по годам; миграции № 1–7 не менялись. Заказчик — слушатель из состава договора, стороннее физлицо с реквизитами в карточке договора, юридическое лицо или ИП из справочника. Ненужные ссылки очищаются при смене типа в черновике. Отдельная карточка слушателя для плательщика не создаётся, место работы слушателя не меняется. Контрагент и его тип повторно проверяются перед формированием.

Один договор включает до 500 существующих подготовительных обучений по одной программе с одинаковым снимком редакции. Разные снимки одной программы не объединяются молча. Можно выбрать часть группы и заключить отдельные договоры с разными заказчиками. Связь с учебной группой не обязательна. Повторное обучение и несколько договоров одного слушателя допустимы. Состояние обучения не изменяется. Быстрый переход к договору есть из группы, состава и индивидуального списка. Внутри карточки вкладки «Договор», «Обучения» и «Заказчик» позволяют заполнить весь черновик без отдельных окон для каждого реквизита.

Деньги хранятся в `total_cents` как целые копейки SQLite с проверкой типа и неотрицательности; обработка и форматирование обходятся без float. Ввод принимает рубли с запятой или точкой и не более двух дробных знаков; ноль допустим. Валюта — RUB. Стоимость общая, распределения по слушателям нет. Условия оплаты — свободный текст; взаимозачёт можно указать как согласованное условие, но бухгалтерского учёта нет. Дата договора — обязательная ISO-дата, исторические даты сохраняются. `created_at`, `registered_at`, `annulled_at` — отдельные фактические времена UTC.

Черновик можно сохранять неполным. Формирование требует выбранных обучений и заказчика с ФИО/наименованием, наименования учебного центра, цены, условий оплаты и подходящего активного шаблона. Заполненные даты и реквизиты физлица проверяются по формату; правовая достаточность набора реквизитов не оценивается. Возраст слушателей проверяется на начало обучения существующим `is_adult`. Текущее образование и основания юридического зачисления не проверяются. Цена, заказчик, условия и состав редактируются только в черновике; `revision` не позволяет затереть сохранение другого окна.

Тип DOCX выбирается по заказчику. Для направления снимка подходят активные варианты `dpo`, `dpo-…`, `po`, `po-…`; несколько вариантов требуют явного выбора, неподходящий `default` не подставляется. Настройка выполняется через реестр шаблонов. `program` заполняется только из `program_snapshot` обучения. `students` — строки выбранных обучений с их датами; одиночные пространства при неоднозначности остаются пустыми (см. [каталог полей](templates.md)). Реквизиты центра читаются компактным SQL по закрытой схеме без зависимости бизнес-сервиса от Qt; данные логотипа не подставляются как объекты. Контекст проходит прежнюю закрытую валидацию, синтаксис движка не расширяется.

Проект сохраняется в `exports/contract-drafts/` с уникальным именем, настоящими данными сторон, номером-заглушкой и видимой отметкой о незарегистрированном состоянии в начале документа. В отличие от него тест в настройках шаблонов полностью вымышленный. Предварительная генерация не занимает номер. Карточка требует сформировать проект и явно подтвердить регистрацию. Отпечаток подтверждения охватывает ревизию черновика, сведения сторон, обучения, снимок программы, группу и версию/хеш шаблона. При регистрации эти сведения читаются заново под write lock; изменение после просмотра приводит к отказу и требованию нового проекта. Окончательный DOCX всегда генерируется заново.

Номер выдаётся внутри `BEGIN IMMEDIATE` по году даты договора: `YYYY-0001`, `YYYY-0002`, …; это технический формат, не утверждённый стандарт центра. Отдельный счётчик и уникальный канонический ключ (`casefold` и нормализация пробелов) исключают дубли при одновременной регистрации и конфликт исторических номеров. Исходный исторический номер хранится до регистрации отдельно от окончательного; он не заменяется новым. Исторический номер вида `YYYY-NNNN` продвигает соответствующий технический счётчик, остальные исторические форматы сохраняются без изменения схемы нумерации. Аннулирование не освобождает номер; неудачная транзакция регистрации не занимает его.

Финальный путь получает `Storage.document_directory(contract_date, "contracts")`: `documents/YYYY/MM/contracts/contract-<UUID>.docx`. Шаблон проверяется по хешу, DOCX публикуется существующим генератором без перезаписи, проверяется его SHA-256, затем в той же SQL-транзакции фиксируются номер, время регистрации, путь, хеш, версия шаблона и структурированный снимок. Снимок содержит использованный контекст (стороны, программа, даты, сумма, условия, номер/дата), IDs обучений, ID программы и метаданные версии шаблона. Изменения справочников и подготовительных обучений не меняют зарегистрированный файл или снимок. Триггеры SQLite запрещают обычную правку/удаление зарегистрированных/аннулированных записей и изменение связей; разрешён только переход зарегистрированного договора в аннулированный с основанием и временем, без изменения остальных данных.

Если генерация не удалась, регистрация и счётчик откатываются. Если файл уже опубликован, а SQL не сохранился, файл переносится в `exports/unregistered-contracts/<UUID>/`. При аварийном завершении возможны файл без записи и временный `.docx-*.tmp`; при открытии реестра `recover_unregistered` под тем же write lock сверяет архив с SQLite и переносит только собственные непривязанные файлы в эту папку. Они не регистрируются автоматически, не перезаписываются и не удаляются. Посторонние имена не затрагиваются, файлы зарегистрированных и аннулированных договоров сохраняются. При недоступности диска проверка сообщает об ошибке, а не создаёт фиктивную регистрацию. Резервные копии должны включать весь каталог данных.

Открытие зарегистрированного/аннулированного договора проверяет SHA-256 и выдаёт копию в `exports/contract-copies/`, без открытия архивного оригинала для правок. Повреждение не исправляется автоматически. Аннулирование требует подтверждения и непустого основания, сохраняет снимок, номер, файл и исходное время регистрации. Это состояние записи, а не юридическая процедура расторжения или подтверждение подписания. Подписи, сканы, правовые способы исправления, роли и полноценный аудит не реализованы.

Windows smoke проверяет активный договор, аннулированный исторический договор и черновик, сохранность снимков/номеров/связей/файлов при обновлении и хеш архивных договоров внутри собранного EXE. Новых зависимостей и сетевых функций нет, U01/S01 не менялись. Реальные формы загружает и проверяет пользователь; юридических текстов, подписей и печатей приложение не придумывает. Приказы и зачисление реализованы в P03.4 (см. ниже).

## Карточка учебного центра

Откройте **Настройки → Учебный центр**. Это реквизиты вашей образовательной организации, отдельно от реестра организаций-заказчиков. Доступны общие сведения, адреса и контакты, банковские реквизиты, сведения о руководителе и лицензии. Поля необязательны: карточку можно заполнять постепенно. Для введённых ИНН, КПП, ОГРН / ОГРНИП, email, БИК и счетов проверяется формат, без проверки контрольных сумм или обращения к внешним реестрам. Дата лицензии вводится как `ГГГГ-ММ-ДД`.

Изменения реквизитов, загрузка, замена и удаление логотипа применяются только кнопкой **Сохранить**. При уходе из формы, смене раздела или закрытии окна можно сохранить изменения, отказаться от них или отменить выход. Повторное открытие приложения восстанавливает сохранённые данные. В каждой базе допустима только одна карточка (`id = 1`); повторное сохранение обновляет её.

Логотип PNG / JPG ограничен 5 МиБ и 25 млн пикселей; проверяется содержимое изображения. Предпросмотр работает до сохранения. Файл сохраняется в `organization/`, в SQLite хранится относительный путь. Перенос хранилища P01.1 сохраняет доступность логотипа. Новый файл записывается до транзакции SQLite: при ошибке записи реквизитов он удаляется, прежний логотип сохраняется. После успешной замены или удаления привязки прежний файл удаляется; если очистка недоступна, интерфейс сообщает об оставшемся файле. Прерывание питания между записью файла и транзакцией может оставить неиспользуемый файл, не заменяя действующий логотип.

Для будущих документов реквизиты должны браться через `TrainingCenterRepository`. При регистрации документа потребуется сохранять снимок использованных реквизитов: последующие изменения карточки не должны менять зарегистрированные, исторические или подписанные документы. Исторические договоры и приказы могут использовать прежние реквизиты. Изменения карточки в будущем должны учитываться журналом аудита. В P02.1 снимки документов, версионирование, реестры, генерация и аудит не реализуются.

## Основа электронного архива

Единый сервис `Storage.document_directory(document_date, category)` создаёт по запросу путь `documents/YYYY/MM/<category>/`. Принимаются категории `contracts`, `orders`, `protocols`, `issued`, `other`. Год и месяц берутся из даты документа, включая исторические даты; пустые годы и категории заранее не создаются. Интерфейс и будущие генераторы должны получать пути только через этот сервис, а в базе хранить пути относительно корня хранилища.

Правила следующих этапов, которые пока не реализуются:

- Новые договоры, приказы, протоколы и выпускные документы формируются и сохраняются автоматически.
- Номер документа хранится и управляется реестром SQLite, а не именем файла.
- Дата документа и фактическая дата внесения учитываются раздельно. Исторические документы могут сохранять первоначальные номера.
- Существующие документы импортируются через контролируемый интерфейс с указанием категории; непосредственное копирование в архив не заменяет регистрацию.
- Изменения зарегистрированных документов фиксируются в журнале; подписанные оригиналы не перезаписываются.
- Изменения карточек слушателей не изменяют исторические документы автоматически.
- Для бумажных оригиналов предусматривается учёт местонахождения.

P01.1 подготовил основу хранения; P02.1 добавил карточку учебного центра, P02.2 — реестр слушателей. P03.3 добавил реестр договоров и их формирование из рабочих карточек. Остальные реестры документов, импорт подписанных оригиналов, права доступа и журнал исправлений остаются для следующих этапов. Ранее применённые миграции сохранены без изменений.

## Windows-сборка

Сборка выполняется только в GitHub Actions: при push и pull request либо вручную через **Actions → Windows — тесты и сборка → Run workflow**. [Workflow](../.github/workflows/windows.yml) устанавливает Python 3.12 и фиксированные зависимости, проверяет безопасность и pytest, собирает приложение в режиме PyInstaller onedir и отдельный helper без Qt. Проверяются запуск EXE дважды, создание SQLite и сценарий обновления собранных EXE с сохранением вымышленных данных. Локальную сборку для обычной разработки не выполняем.

Команды сборки из CI (PowerShell):

```powershell
python -m PyInstaller --noconfirm --clean --onedir --windowed --name Proficentr --paths src run_proficentr.py
python -m PyInstaller --noconfirm --clean --onefile --windowed --name ProficentrUpdater --paths src run_updater.py
```

Затем CI упаковывает всю папку `dist/Proficentr` в `Proficentr-X.Y.Z-Windows.zip`, где версия берётся из приложения, и загружает артефакт `Proficentr-Desktop-Windows` со сроком хранения 14 дней. Обычный workflow не публикует стабильные версии. Как получить и распаковать проверочную сборку — в [README](../README.md#установка); контролируемый выпуск, подпись пакета, защиты GitHub и ограничения проверки — в [updates.md](updates.md#защищённый-выпуск).

Не добавляйте в Git персональные данные, сканы, рабочие базы и секреты; соответствующие файлы и каталоги включены в `.gitignore`. Статус лицензии указан в [README](../README.md#исходный-код-лицензия-и-обратная-связь).


## Приказы и зачисление (P03.4)

`EnrollmentOrderRepository` отделён от Qt и договоров; использует прежние `TemplateRepository`, закрытый контекст и DOCX-движок. Черновик хранит дату, вид, группу, выбранные существующие обучения и вариант формы. Одна программа и одинаковый снимок её редакции обязательны; проверяются существование слушателя/программы, возраст 18+ на начало, даты и отсутствие зачисления. Частичный состав группы допустим. Заказчики могут различаться. Программа и направление фиксируются в снимке приказа из выбранных обучений.

Регистрация под `BEGIN IMMEDIATE` повторно проверяет отпечаток проекта, включая сведения слушателей/центра, обучения, состав группы, связанные договоры и активную версию шаблона. Независимый годовой счётчик выдаёт `З-YYYY-NNNN`; исторический номер уникален без учёта регистра и лишних пробелов. Исторический номер такого же формата продвигает счётчик соответствующего года. Проект не занимает номер. Регистрация сохраняет снимок контекста, выбранных обучений, состава группы на момент оформления, связей договоров и версии формы, а также SHA-256 и DOCX в `documents/YYYY/MM/orders/order-<UUID>.docx`. Исправления источников не меняют архив. Триггеры блокируют редактирование реквизитов, состава и удаление зарегистрированного приказа.

Подтверждение фактического подписания — отдельная транзакция. Сотрудник указывает дату подписания, ФИО ответственного и подтверждает проверку оснований/договоров и применимых условий допуска/образования. Программа сохраняет отдельное фактическое время подтверждения UTC, но не проверяет подлинность подписи, договоров и юридическую достаточность оснований. Дата подписания — между датой приказа и текущей датой. Изменение оснований обучения после регистрации требует нового приказа; повторное зачисление одной записи запрещено. Зарегистрированный DOCX не меняется. Другие обучения слушателя не меняются. Подписание договоров не учитывается: наличие зарегистрированного договора не означает его подписание. Отсутствие договора показывается предупреждением и требует ручной проверки, фиктивные договоры не создаются.

Миграции № 1–8 неизменны. Вместо пересоздания `trainings` добавлена `training_enrollments`: один `training_id` связан с конкретным подписанным приказом и его неизменяемым составом через внешние ключи (статус проверяется отложенным FK). Эффективное состояние `enrolled` вычисляет `TrainingRepository`; исходный столбец `trainings.state` сохраняет ограничение миграции № 6. Добавление связей и переход приказа в `signed` атомарны. Триггеры запрещают изменение/удаление зачисленного обучения, удаление/подмену связи и смену программы его группы. Название и плановые даты группы можно менять, без переписывания индивидуальных периодов. Это защита от обычных операций, не защита локальной SQLite от владельца диска.

Открытие документа выдаёт отдельную копию с проверкой SHA-256. При сбое регистрации номер и БД откатываются; непривязанный файл сохраняется отдельно в `exports/unregistered-orders/`. Проверка при открытии раздела под тем же writer lock перемещает собственные архивные DOCX/временные файлы без регистрации в этот каталог, не присваивая им номер и не удаляя. При физической недоступности диска перемещение может не завершиться; повторная проверка выполняется при следующем открытии.

Пакет — новая локальная папка `exports/enrollment-packages/<UUID>/`: проверенная копия зарегистрированного/подтверждённого приказа, дедуплицированные связанные действующие зарегистрированные договоры и текст с предупреждениями. Черновые/аннулированные договоры не включаются. Любое повреждение включаемого архива отменяет подготовку; собственная неполная папка удаляется, оригиналы сохраняются. Пакет не является универсальным обязательным комплектом, согласия не создаются автоматически. Сетевой передачи нет.

Windows update smoke сохраняет зарегистрированный и подтверждённый приказы, версии форм, номера, даты, снимки, подтверждения, связи и файлы при замене собранного приложения U01; проверяет вычисляемые состояния и локальный пакет. Механизмы обновления/доверенные ключи U01/S01 не менялись. Роли, аудит, электронная подпись, произвольная отмена подтверждённого приказа, отчисление, перевод, аттестация, выпуск, PDF и ФРДО в P03.4 не реализованы.

## Аттестация и протоколы (P04.1)

`AttestationRepository` и модели `AttestationProtocol` / `AttestationResult` отделены от Qt. Миграция № 10 добавляет `attestation_protocols`, `attestation_results` и независимый годовой счётчик `attestation_sequences`; миграции № 1–9 не изменены. Результат связан через постоянный `training_id` с `training_enrollments`, без записи в карточку слушателя и без изменения защищённых обучений/зачислений. Выбор доступен после подтверждения приказа P03.4. Один протокол включает одно обучение или выбранную часть одной группы, одну программу и одинаковые снимки её редакции; ДПО и ПО разделены. Дата аттестации общая для включённых попыток. Комиссия хранится непосредственно в протоколе.

Черновик допускает незаполненные результаты. Регистрация под `BEGIN IMMEDIATE` повторно проверяет отпечаток сведений, индивидуальных результатов и активной версии формы. Присваивается `П-YYYY-NNNN` по году даты протокола. Исторический номер нормализуется для уникальности без учёта регистра/лишних пробелов; номер штатного формата продвигает соответствующий годовой счётчик. Использованные номера не освобождаются; триггеры запрещают удаление зарегистрированного протокола, удаление/уменьшение счётчика. Дата документа, дата аттестации, создание и регистрация хранятся отдельно, фактические метки времени — UTC.

Снимок фиксирует реквизиты центра, данные слушателей, программы и редакции из обучений, индивидуальные периоды и результаты, комиссию, номер/даты и версию формы. Используется существующий закрытый контекст DOCX и генератор без расширения исполняемого синтаксиса. Архив — `Storage.document_directory(protocol_date, "protocols")`, файл `protocol-<UUID>.docx`, отказ от перезаписи. При ошибке SQLite, включая ошибку COMMIT, транзакция откатывается, собственный опубликованный файл перемещается в `exports/unregistered-protocols/`. После аварийного завершения такие DOCX/временные файлы обнаруживаются под writer lock при открытии раздела и перемещаются отдельно без регистрации. При физической недоступности диска операция восстановления повторяется после восстановления доступа. Открытие выдаёт отдельную копию с проверкой SHA-256; повреждённый оригинал автоматически не восстанавливается.

Зарегистрированные результаты неизменяемы уже до подписания: исправление требует отдельного протокола. Подписание подтверждается сотрудником с указанной датой, ответственным и отдельным временем подтверждения. Пустой результат хотя бы одного слушателя блокирует подтверждение в репозитории и SQLite. Оценка, квалификация и разряд необязательны и автоматически не присваиваются. Программа не проверяет юридическую достаточность формы/комиссии и подлинность подписей. Подтверждение не меняет DOCX, снимок или индивидуальные результаты. SQLite-триггеры защищают от обычного изменения, а не от владельца локальной базы.

Каждая попытка сохраняется отдельно. `history(training_id)` возвращает историю, `current_confirmed_result(training_id)` выбирает только `signed` по убыванию даты аттестации, затем постоянного ID протокола. Более ранний исторический протокол или позднее подтверждение старой попытки не подменяют более поздний результат; черновики и только зарегистрированные протоколы не влияют на выбор. Успешность не имеет приоритета над датой: последующий подтверждённый отрицательный результат тоже актуален.

В «Документах» добавлена вкладка протоколов с поиском, составом, таблицей результатов, комиссией, выбором формы, проектом, регистрацией, подтверждением и открытием архивной копии. Быстрые действия доступны из группы, её состава и индивидуального обучения. Windows update smoke дополнен проверкой нескольких попыток, подтверждённого и только зарегистрированного протоколов, актуального результата, форм, счётчика и архивных файлов после обновления U01. Механизмы обновления U01/S01 не менялись.

Завершение обучения, выпускные документы, реестры выдачи, PDF, ФРДО, апелляции, справочники комиссий и электронная подпись в P04.1 не реализуются. Перед эксплуатацией формы протоколов требуют отдельной юридической проверки и согласования.

## Завершение обучения и приказы (P04.2)

`CompletionRepository`, модели `CompletionOrder` / `CompletionEntry` и UI работают отдельно от зачисления и аттестации. Миграция № 11 добавляет только `completion_orders`, `completion_order_trainings`, `training_completions`, независимый счётчик `completion_sequences`, индексы и защитные триггеры. Миграции № 1–10 неизменны. Записи `trainings`, `training_enrollments` и исходные документы не переписываются. `TrainingRepository` вычисляет состояние `completed` по факту завершения с приоритетом над `enrolled`; `excluded` по-прежнему относится к подготовительным записям. Прежние ограничения редактирования зачисленного обучения продолжают защищать и завершённые записи.

Для оформления требуются подтверждённое зачисление и актуальный подписанный успешный результат. Выбор основания использует существующий `AttestationRepository.current_confirmed_result()`: дата аттестации, затем постоянный ID протокола. Индивидуальный приказ включает одно обучение; групповой — выбранную часть одной группы, одну программу и одинаковые снимки её редакции. Направление проверяется по снимку обучения и протоколу. Каждая строка хранит свою фактическую дату, которая не может предшествовать началу обучения или аттестации-основанию. Плановое окончание предлагается в интерфейсе, но не записывается обратно в обучение и может быть исправлено для приказа.

У существующего индивидуального результата нет отдельного числового ID: его постоянный ключ — `(protocol_id, training_id)`. Состав приказа ссылается на этот ключ через FK и хранит снимок номера/дат/вида протокола, сведений о подтверждении подписания, результата, оценки, квалификации и разряда. Факт завершения ссылается на неизменяемую строку приказа, конкретный протокол, обучение и фактическую дату. `training_id` — первичный ключ факта, поэтому дважды завершить одно обучение нельзя. Отложенный FK требует подписанного приказа к COMMIT.

Черновик сохраняется без номера и факта завершения. Регистрация под `BEGIN IMMEDIATE` повторно проверяет отпечаток черновика, реквизитов, состава, оснований и активной формы. Счётчик по году даты приказа выдаёт `О-YYYY-NNNN`, независимо от договоров, приказов о зачислении и протоколов. Исторические номера нормализуются для уникальности без учёта регистра/лишних пробелов; номер штатного формата продвигает счётчик соответствующего года, меньший исторический номер не уменьшает его. Использованные номера сохраняются; триггеры запрещают удаление зарегистрированных приказов и уменьшение/удаление счётчика.

Используются прежний DOCX-движок и закрытый контекст; добавлены только поля завершения. Подбираются точные активные варианты `completion_order`: `dpo-individual`, `dpo-group`, `po-individual`, `po-group`. Для разных фактических дат требуется вывод `row.completion_date` внутри цикла `students`; общая дата остаётся пустой. Снимок регистрации фиксирует центр и руководителя, слушателей, программу из обучений, плановые и фактические даты, конкретные основания, результаты и версию формы. Архив — существующий `Storage.document_directory(order_date, "orders")`, файл `completion-order-<UUID>.docx`. Префикс отделяет его от приказов о зачислении; оригиналы не перезаписываются. При открытии проверяется SHA-256 и выдаётся отдельная копия.

При ошибке регистрации, включая COMMIT, SQLite и номер откатываются, собственный опубликованный файл переносится в `exports/unregistered-completion-orders/`. После аварии собственные непривязанные DOCX/временные файлы обнаруживаются под writer lock при открытии раздела. Архивные приказы о зачислении не перемещаются. При недоступности диска восстановление повторяется после восстановления доступа. Повреждённые оригиналы автоматически не заменяются.

Подтверждение подписания требует даты, ответственного и явного подтверждения проверки остальных необходимых условий завершения. В UI отдельно подтверждается наличие подписанного приказа. Дата подписания не раньше приказа и фактических дат завершения, не позже сегодняшней даты; исторические даты допустимы, время внесения хранится отдельно в UTC. В одной транзакции повторно проверяются актуальный `passed`, точный ID основания, даты и архивные файлы, создаются все факты и приказ переводится в `signed`. Изменение актуального основания после регистрации, включая новый успешный протокол, требует нового оформления: зарегистрированный документ нельзя незаметно связать с другим результатом. Сбой на одном слушателе откатывает все факты и подтверждение. Триггеры блокируют неподтверждённый/неуспешный результат, повторное завершение, изменение фактов, зарегистрированного состава и снимка; FK требует согласованности факта и подписанного приказа.

Новые аттестации после завершения не меняют его историческое основание. Неуспешный результат не означает отчисление, а подписание протокола не завершает обучение. Завершение не означает выдачу удостоверения, диплома или свидетельства. Проверка применимых требований и локальных актов остаётся за ответственным сотрудником; подлинность подписей программа не проверяет. Это защита от обычного редактирования, а не криптографическая защита локальной SQLite.

В «Документах» добавлена вкладка приказов о завершении без нового пункта боковой навигации. Группы и индивидуальные обучения показывают эффективное состояние, подтверждённый результат и основание; доступны быстрые переходы к оформлению. Windows update smoke сохраняет подписанный и только зарегистрированный приказы, даты, состав, основания, снимки, факт завершения, шаблон, счётчик и архивные файлы; повторное завершение после обновления отклоняется. Механизмы U01/S01 не менялись. Выдача документов, ФРДО, PDF, отчисление, перевод, отмена и сложные исправления не реализуются в P04.2.

## Выпускные документы и передача (P04.3)

`IssuedDocumentRepository` и `DeliveryRepository` разделяют оформление и фактически выполненную передачу. Миграция № 12 добавляет только `issued_documents`, `issued_sequences`, `document_transfers`, `transfer_evidence` и необходимые индексы/триггеры. Миграции № 1–11 неизменны; обучения, зачисления, аттестации и завершения не переписываются. Частичный уникальный индекс допускает один основной зарегистрированный документ на обучение в текущем процессе. Дубликаты и контролируемые замены потребуют отдельного процесса и миграции; они не имитируются удалением оригинала.

Основание — защищённый факт `training_completions`, подписанный приказ о завершении и конкретный сохранённый результат `(protocol_id, training_id)`. Проверяется существование слушателя и зачисления. ФИО, центр/руководитель, программа, часы, плановые и фактические даты, квалификация и разряд берутся из исторического снимка завершения. Актуальные карточки не подменяют их; более поздняя неуспешная аттестация не отменяет исторический факт завершения. Скалярные поля выпускного документа структурированно сохраняют тип, ФИО, программу, направление/вид, часы, квалификацию, даты и реквизиты приказа; извлекать их из DOCX для будущих этапов не требуется. Достаточность этих сведений для официальной ФИС ФРДО не заявляется.

Структурированные виды `dpo_upskilling`, `dpo_retraining` и все три вида ПО однозначно определяют три типа выпускных документов/шаблонов. Новые типы шаблонов используют прежний закрытый контекст и генератор; исполняемый синтаксис не менялся. Регистрация под `BEGIN IMMEDIATE` повторно проверяет отпечаток черновика, исторического основания и активной формы. Независимые области `(вид, год)` выдают `У-YYYY-NNNN`, `Д-YYYY-NNNN`, `С-YYYY-NNNN`. Исторический номер уникален в области вида без учёта регистра/лишних пробелов; штатный исторический номер продвигает счётчик соответствующего года. Черновики не занимают номера. Реквизиты бланка проверяются отдельно: уникальна тройка «вид документа, нормализованная серия, нормализованный номер бланка» для зарегистрированных документов с заполненным номером бланка. Бланки автоматически не нумеруются; пустая серия и отсутствие номера допустимы.

Архив — `Storage.document_directory(document_date, "issued")`, `documents/YYYY/MM/issued/issued-<UUID>.docx`. Файл создаётся без перезаписи; открытие выдаёт копию после SHA-256. Зарегистрированные реквизиты, снимок, номер, файл и версия формы защищены триггерами, включая INSERT OR REPLACE и UPDATE OR REPLACE другого черновика с конфликтом ID, обучения, регистрационного номера или бланка. При сбое, в том числе COMMIT, номер и SQLite откатываются, собственный опубликованный файл перемещается в `exports/unregistered-issued/`. При открытии раздела под writer lock непривязанные собственные файлы/временные файлы сохраняются отдельно. Физическая недоступность диска может отложить перенос до восстановления доступа.

Пакет состоит из отдельных документов. Сотрудник выбирает завершённые записи, исключает строки, проверяет индивидуальные даты/бланки/формы, генерирует проекты и явно регистрирует подготовленные. Для каждого документа своя транзакция; частичная ошибка показывается в строке. Повторная попытка возвращает уже зарегистрированный основной документ, не создавая дубль. Поиск и фильтры работают по историческим ФИО/программе, виду, году и состоянию; отдельный список показывает завершённые обучения без зарегистрированного документа.

Передача — неизменяемый журнал. Личное вручение фиксирует получателя, дату и способ подтверждения. Почтовая отправка хранит адрес, трек при наличии и состояние отправки/неподтверждённого вручения; трек не означает вручение. Подтверждение вручения — новое событие со ссылкой на исходную отправку того же документа, фактической датой вручения и описанием подтверждения; исходная запись не меняется. Email фиксирует отправку/подтверждённое получение электронной копии и не влияет на факт передачи оригинала. Общего состояния «выдан из-за DOCX» нет. События допустимы только для зарегистрированных документов; время внесения хранится отдельно в UTC. Даты событий — не раньше даты документа и не позже сегодняшнего дня.

Подтверждения копируются в `attachments/issued-evidence/evidence-<UUID>.<pdf|png|jpg>`, без бинарных данных в SQLite. Ссылки хранят SHA-256, формат, вид подтверждения и событие. Триггеры вставки защищают также уникальный путь подтверждения и ссылку почтового вручения от замены через INSERT OR REPLACE. Исходники и прежние подтверждения не меняются; символические ссылки, сетевые/облачные пути, выход из архива и перезапись отвергаются. PNG/JPG проходят существующую проверку `read_logo` (до 5 МиБ и 25 млн пикселей), PDF — проверку заголовка/окончания и разбор существующим Qt PDF (до 10 МиБ, хотя бы одна страница, без пароля). PDF не генерируется. При ошибке записи/SQLite/COMMIT собственный файл удаляется, событие/ссылка откатываются; аварийные непривязанные файлы сохраняются в `exports/unregistered-evidence/`. Просмотр выдаёт проверенную копию; подлинность подписей и сканов не проверяется.

Внутренний XLSX создаётся `openpyxl==3.1.5` с фиксированной транзитивной зависимостью `et_xmlfile==2.0.0`. Экспортирует зарегистрированные документы за выбранный период и вид: номера/даты, бланки, ФИО, программу, дату завершения, подтверждённую передачу оригинала и отдельно электронную копию. Паспорта/СНИЛС не экспортируются. Все ячейки явно строковые (`data_type='s'`), включая строки с `=`, `+`, `-`, `@`; формулы и гиперссылки не создаются. Путь `exports/issued-registers/internal-register-<UUID>.xlsx`, отказ от перезаписи. Это внутренний реестр, не официальный шаблон ФИС ФРДО.

Windows smoke проверяет в собранном EXE чтение выпускного архива/подтверждений и создание XLSX; update smoke сравнивает документ, форму, счётчик, события, файлы подтверждения и основание после обновления U01. Механизмы U01/S01 не менялись. Стабильный релиз не публикуется. ФИС ФРДО, отправка писем/почты, PDF-генератор, дубликаты, аннулирование и сложные исправления относятся к будущим этапам.
